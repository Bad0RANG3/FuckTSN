# 判定链路：服务端到底怎么判「合格」

这份文档只写**实测出来的事实**，每条后面都跟着证据来源。凡是没验证过的，标 `（未验证）`。

---

## 一、一张图看完

```
App                      网关(tsn-gateway)                 业务服务(upms/exercise)
 │                              │                                  │
 │ 1. GET  getExerciseSetting   │                                  │
 ├─────────────────────────────►│── 禁跑？ ──► 999 + code:1 msg="黑名单" │
 │                              │                                  │
 │ 2. GET  getExerciseStartTime │                                  │
 ├─────────────────────────────►│── 返回 startTime（毫秒）           │
 │                              │                                  │
 │ 3. POST exerciseRunningFace  │                                  │
 ├─────────────────────────────►│── 存人脸 + 与底库比对 ──────────────►│
 │                              │                                  │
 │ 4. POST addExerciseRecord    │                                  │
 ├─────────────────────────────►│── 判分（下面第二节）──► status/sportStatus/remark
 │                              │                                  │
 │ 5. GET  getExerciseRecord    │                                  │
 ├─────────────────────────────►│── 回读判定结果                     │
```

关键点：**判定全在服务端**。客户端提交体里能控制的只有原始素材（点串、步数、里程、
时间、environment、identify），`status`/`sportStatus`/`remark`/`va`/`isValid` 这些结论
字段传什么都会被丢弃重算（实测：在加密前往 params 里注入这些字段，回读仍是服务端自己
算的值）。

## 二、`addExerciseRecord` 之后的判分顺序

按我们 6 条被罚记录的回读 `remark` 反推，服务端是**逐项短路**的：

| 顺序 | 检查 | 失败时的 `remark` | 证据 |
|---|---|---|---|
| 1 | 人脸（该 identify 有没有对应的人脸记录、是否在允许范围） | `人脸对比超出规定范围-黑名单15` | 同一条轨迹，不带人脸 → 人脸错；带人脸 → 进到步数判定 |
| 2 | 步数（相对里程的下限） | `运动步数不符合131310-黑名单15` | 2.09 km / 999 步被拦，同参数 1099 步通过 |
| 3 | 轨迹质量（配速、步频、速度峰值、围栏…） | 前半段写 `合格`，后半段接处罚 | 有记录 `remark` 直接是 `合格131310-黑名单15` |
| 4 | 处罚拼接 | `…-黑名单15` | 处罚期内每条都带，与 `startTime` 无关 |

`remark` 里的数字后缀（`131310`、`10`）是服务端内部码，**不是**步数阈值 —— 它在「合格」
记录上也出现过。

### 2.1 处罚是按「提交时刻」算的

同一批提交里，`startTime` 覆盖 11-10 ~ 11-20 的 6 条记录，全部带上当次处罚标记。把记录
日期改到十天前，判定照样往下走（人脸/步数/合格），**没有「提交超时」这类拒绝**。

→ 结论：处罚挂在账号上，跟着「什么时候提交」走；回填历史日期不会绕过处罚，只会让每一条
都被判一遍。

### 2.2 禁跑只拦读接口

`getExerciseSetting` 被 `999 + code:1` 拦住（`runType` 0–7 × 两套校区坐标共 16 组
全拦），但：

- `getExerciseStartTime`、`sumExerciseRecord`、`listExerciseRecord`、`statisticsExerciseRecord` 全部正常；
- **`addExerciseRecord` 没有禁跑校验** —— 空 body 也能建出一条记录。

所以「禁跑期不能跑」是**业务约定**，不是技术封锁。但对考试没用：处罚期内提交的记录一律
`status=0`，不计次数。

## 三、哪些字段服务端真的用

| 字段 | 是否参与判定 | 依据 |
|---|---|---|
| `sportRange` / `gpsDistance` | **强参与**，且**不做点串重算** | 5 条合格记录点串累加比上报多 +0.53%~+37.1%（最长那条 +37% 照样合格）；被罚那条恰好贴 `rangeSetting` |
| `step` / `stepNumbers` | **强参与** | 999 步（2.09 km）→ `运动步数不符合131310`；同里程 1015 步 → `合格`；门槛是 `stepSetting=1000` |
| `sportTime` + 起止时间 | **强参与** | 窗口按**分钟**：6–21 min，超距离按比例放大（4.01 km → 41 min） |
| `isFaceStatus` / 人脸接口 | **强参与，且是短路口** | face=0 的记录 `remark` 直接是人脸原因，不再检查步数；`remarkExp` 说明超范围的是**识别位置** |
| `identify` | **强参与** | 合格记录全是 UUID（大小写都行）；被罚那条是 `"1"` |
| `appVersion/brand/model/system/version` | **强参与（画像一致性）** | 唯一被判 `数据异常-作弊嫌疑` 的记录是 `2.0.23 + Xiaomi + Android 14`；合格记录全是 `3.6.814 / iPhone 17 Pro / iOS 27.0.1|27.3` |
| `gitudeLatitude`（点串） | 弱参与（质量抽检） | 服务器不按点串算距离；只看键是否齐、时间戳是否递增、步数累计是否对得上 |
| `environment` | 弱参与（有独立接口回传） | `safe`/`oppo` 是客户端自检结果，没有观察到它单独导致拦截 |
| `d/f/m/h`、`isValid`、`remarkId` | 客户端标志位 | 传 0 不报错，传 1 也不加分；`fail3` 回显 `isValid:null` 但 `remark` 是 `合格` |
| `status`/`sportStatus`/`reachRange`/`va` | **只读回显** | `reachRange==sportRange` ⇔ 计入成绩；`va ∈ {正常, 我要申诉}` |

## 四、「合格」的可执行门槛（原表已被真实数据推翻，见 `docs/合格规格.md`）

早期版本按"生理常识"标定过一版阈值，后来用 5 条真实合格记录逐条核对，发现**一半是误判**。
现在的分档原则：只有被服务器亲口拒绝过的才进硬闸门，其余降为经验提醒。

| 项 | 硬闸门（`server` 档） | 早期错误阈值 | 为什么错 |
|---|---|---|---|
| 里程 | ≥ `rangeSetting`（留 2%+ 余量） | 同 | 一致 |
| 步数 | ≥ `stepSetting` | `max(stepSetting, 里程/1.20)` | 对 2.09 km 会要求 1742 步，而真实合格记录只有 1015–1099 步 → 必误杀 |
| 步幅 | 无（0.55–4.00 只提醒） | 0.62–1.20 m | 合格记录实测 0.953–3.787 m，`limitStride=2.3` 根本没被执行 |
| 步频 | 无（40–200 只提醒） | 145–195 spm | 合格记录实测 47.2–128.5，`limitStepFrequency=300` 也没被执行 |
| 60 s 步数桶 | 求和 == `step`（硬） | 110–210 | 到位实测单段 0–171，头部 0 和尾部 33 都出现过 |
| 配速 | 180–600 s/km（3′–10′），建议 240–540 | 同 | 一致，但被罚那条正好 `10'00"` → 要离边界远 |
| 起跑时段 | **无时段限制**，只要求不跨日 | 06:00–21:00 | `startQualifiedTimeSetting=6` 是**分钟**不是小时；实测 21:10 开跑合格 |
| 时长窗口 | `start/endQualifiedTime` 分钟，超距离按比例放大 | 未纳入 | 4.01 km 那条上限是 41 min，只按 21 min 判会误杀 |
| 围栏 | 越界点 ≤10% | 同 | 一致 |
| 点串长度 | 不得短于上报 −0.2%（硬）；上限只提醒 | +0.2%~+6% | 合格记录最长 +37.1%，硬卡必误杀 |
| 点数/采样 | 1 点/秒（中位 1000±15 ms 硬） | 整秒对齐 | 1125/4984 点带 ±2 ms 抖动，每条还有 6–29 个 `dt=0` 重复秒 |
| 字段 | 9 键 `a c e i l m o s t` 全字符串 | 同 | 一致 |
| 人脸 | 三类都传 + 识别位置在规定距离内 | 只要求 `isFaceStatus=1` | face=1 也可能因**位置超范围**被判 |

分档实现见 `compliance.py`（`TIER_PROTOCOL / TIER_SERVER / TIER_HEURISTIC / TIER_SELF`，
`mode ∈ {strict, balanced, compatible}`），回放验证见 `tools/audit_gates.py`。

## 五、管理面为什么进不去（结论）

| 尝试 | 结果 |
|---|---|
| `/upms/auth/oauth/token` 8 种 grant、7 组 client | 全 `428 验证码不能为空`；无头时 `请求头中client信息为空` |
| `/code?randomStr=`（出图接口，5 种参数形式） | 恒 `500 {"message":"No value present"}` —— 映射没部署 |
| `/token/login`（登录页） | 404 |
| 学生 token 打 `/upms/basUser/*`、`/upms/exerciseRecord/*` | `{"code":1,"msg":"不允许访问"}` 或 404 |
| `/upms/actuator/*` | 只开 `self/health/health-path`；`env/beans/heapdump` 403（Tengine「网站防火墙」） |
| 源站 IP 的 9999/8080/8443/3306 | 全 timeout（安全组丢包） |

→ 闸门顺序是「头存在性 → 验证码 → client 认证 → grant 分派 → 用户凭证」，而第一步的验证码
接口本身是坏的 —— **对外所有人（包括管理员）都登不进管理端**。改服务端数据这条路，在
网络层就不存在入口。

## 六、还剩什么风险

1. `addTime` 是服务端时间，**伪造不了**；回填历史日期必然留下「提交时刻 ≠ 结束时刻」的痕迹。
   实测 ≤10 天不会被拒，但这是可观测特征。
2. 处罚终点由最后一次违规提交决定（每条 +15 天）。
3. 学期截止日期只存在于被禁跑拦住的 `getExerciseSetting` 里，禁跑期间查不到。
