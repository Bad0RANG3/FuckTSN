# 合格规格（公有接口 v3.6.814）

> 本文件只写**有证据的结论**。每条都标注证据来源：
> - `[回显]` 服务器返回的字段原文（`repo/_probe/hist.json`、`audit.json`、`failrec.json`）
> - `[对比]` 同一指标下"通过 vs 被拒"的对照样本
> - `[逆向]` APK 反编译出的调用链
> - `[推断]` 由以上事实推出，未直接观测到
>
> 复核方式：`python tools/audit_gates.py`（14 条真实记录回放）、`python -m pytest tests -q`。

---

## 0. 一句话结论

一条记录能不能合格，取决于 5 个**上报标量**和 1 个**外部动作**：

| # | 决定项 | 取值来源 | 服务器拒绝时的原话 |
| --- | --- | --- | --- |
| 1 | `step` ≥ `stepSetting` | 请求体 | `运动步数不符合131310` |
| 2 | `sportRange` ≥ `rangeSetting` | 请求体 | （与其他项合并成）`数据异常-作弊嫌疑` |
| 3 | `sportTime` 落在时长窗口内 | 请求体 | `合格` / 不通过 |
| 4 | 三类人脸都传到、且**识别位置在规定距离内** | 人脸接口 | `人脸对比超出规定范围` |
| 5 | `identify` 必须是 UUID | 请求体 | `数据异常-作弊嫌疑` |
| 5b | 设备画像是新 App（`3.6.814/iPhone/iOS`） | 请求体 | 同上（**软**：只有相关性证据，见 3.5） |
| 6 | 每天只提交一条、学期配额没用完 | 账号 | `今日已提交` / 配额 |

**轨迹点位不参与距离判定。** 服务器只信 `sportRange`/`gpsDistance` 这两个上报值，
5 条合格记录的点位链长比上报里程多出 +0.53% ~ **+37.1%** 都照收 `[对比]`。
点位只被用来做"像不像真跑过"的抽检（时间戳形态、键齐不齐、步数累计对不对）。

## 1. 判定发生在服务端，客户端字段全被重算

- `status`/`sportStatus`/`remark`/`va`/`isValid` 都是**回显**，不是入参。
  我们传 `isValid=1` 的那条照样被判死；`fail3` 里回显 `isValid: null`，`remark` 却是 `合格131310-黑名单15` `[回显]`。
- 判定顺序是短路式的：**人脸 → 步数 → 轨迹质量 → 处罚拼接**。
  人脸这条记录 `isFaceStatus="0"`，`remark` 直接就是人脸原因，没有再去检查步数 `[对比]`。
- 处罚（`-黑名单15`）是**账号级**的、在提交那一刻挂上去的：6 条记录带这个后缀，
  其中 `remark` 明确写着 `合格` `[回显]`。所以"remark 里有合格"不等于账号没事。

## 3. 硬闸门（`TIER_SERVER`，不满足必然被拒）

### 3.1 步数：`step` ≥ `stepSetting`

| 步数 | 里程 | 结果 |
| --- | --- | --- |
| **999** | 2.090 | ❌ `运动步数不符合131310` |
| 1004 | 2.050 | ✅ 合格 |
| 1015 | 2.090 | ✅ 合格 |
| 1059 | 4.010 | ✅ 合格 |
| 1099 | 2.140 | ✅ 合格 |
| 2013 | 2.020 | ✅ 合格 |
| 2109 | 2.010 | ✅ 合格 |

`stepSetting = 1000` `[回显]`。**门槛就是 `stepSetting`，不是"步幅窗口"**：
999 步 / 2.09 km（步幅 2.09 m）被判死，1015 步 / 2.09 km（步幅 2.06 m）合格 —— 两者步幅几乎一样，
差的是那 16 步。合格记录里步幅从 0.95 m 到 3.79 m，服务器一个都没管 `[对比]`。

### 3.2 里程：`sportRange` ≥ `rangeSetting`

`rangeSetting = "2.000"`。被罚那条正好 `2.000`（贴线），合格记录是 `2.010 / 2.020 / 2.050 / 2.090 / 2.140 / 4.010`。
**留 2% 以上余量**（推荐 2.10–2.35 km @2 km 场次）。`gpsDistance` 必须与 `sportRange` 同值 `[逆向]`。

### 3.3 时长：`sportTime` ∈ [`startQualifiedTime`, `endQualifiedTime`] 分钟

- 两个设置项的单位是**分钟**，不是小时：`startQualifiedTimeSetting=6`、`endQualifiedTimeSetting=21` `[回显]`。
- 距离超过一圈时服务器自己放大上限：4.010 km 那条记录的 `endQualifiedTimeSetting` 是 **41** `[回显]`。
- 实测时长 880 / 887 / 940 / 1027 / 1041 / 1347 s 全部落在窗口内（14.7 / 14.8 / 15.7 / 17.1 / 17.35 / 22.45 min）。
- **没有"早上 6 点到晚上 21 点"这种时段限制**：真实合格记录开始时间 18:14、18:57、19:32、20:01、**21:10** `[回显]`。
  之前把 `startQualifiedTime=6` 当成"6 点"是彻底读错了字段。

### 3.4 人脸：三类都要传，且识别位置要在规定距离内

- `isFaceStatus` 必须是 `"1"`；人脸那条记录是 `"0"`，直接判 `人脸对比超出规定范围` `[对比]`。
- `remarkExp` 把原因写全了：*"您在跑步中途进行人脸识别时超规定范围，系统要求需要在规定距离范围内
  进行人脸识别，而您人脸识别的实际识别距离超过范围"* `[回显]`。
  → 中间人脸的 `coordinates` 不能随便取，要落在 `getExerciseSetting` 下发的 `middleFaces` 比例点上，
  且这几个比例点本身要在允许距离区间内 `[推断：由 remarkExp 措辞与比例机制共同支撑]`。
- 人脸是**最短路口**：人脸没过就不会去看步数，所以先修人脸再调步数 `[逆向]`。

### 3.5 身份与设备画像

- `identify` 必须是 UUID。合格记录里小写 `4b1eed60-…` 和大写 `5487F28C-…` 都有 → 大小写不敏感 `[回显]`。
  被罚那条是 `"1"`。
- 设备画像：`appVersion 3.6.814 / iPhone / iPhone 17 Pro / iOS / 27.0.1 或 27.3` `[回显]`。
  唯一一条 `2.0.23 + Xiaomi + Android 14` 就是被判 `数据异常-作弊嫌疑` 的那条 `[对比]`。
  严格说这是"画像一致性"证据：单看设备不能证明因果，但它是我们手里唯一能解释"作弊嫌疑"的字段组。

### 3.6 配速：3′00″–10′00″/km，且不要贴边

- 规则原文上下限：3 分钟 / 10 分钟每公里 `[逆向]`。
- 被罚那条配速恰好 `10'00"`、时长恰好 `1200 s`、里程恰好 `2.000 km` —— 三个整数 `[回显]`。
  合格记录配速 `5′36″ / 6′55″ / 7′02″ / 7′13″ / 7′45″ / 7′47″ / 7′52″ / 7′59″ / 8′03″ / 8′38″`。
- 结论：窗口内 + **离边界远一点**（我们自用 6′30″–9′00″）。

### 3.7 报文可解析（协议层，违反直接 403/999）

- 点位 9 键齐全：`a c e i l m o s t`，值**全部字符串** `[回显，4984/4984 点]`。
- `stepNumbers` 是字符串化的整数数组，**求和必须等于 `step`** `[回显，5/5]`。
- 末点 `i="true"`、末点 `e == step` `[回显，5/5]`。
- `t` 是毫秒时间戳字符串。

### 3.8 频率与配额

- 每天一条：`sum.sunRun.succeed = 6`，`leaveTotalCountZong = 34`，`qualifyTotalCount = 40` `[回显]`
  → 学期 40 条、80 km 的配额，已用 6 条。
- 同一天重复提交会被判"今日已提交" `[逆向]`。

## 4. 经验区间（`TIER_HEURISTIC`，超出只提醒，不是判定）

这些指标全部**在合格记录里出现过"不像真人"的取值**，所以任何把它们当硬闸门的实现都会误杀：

| 指标 | 5 条合格记录实测 | 我们的提醒区间 | 备注 |
| --- | --- | --- | --- |
| 步幅 = 里程/步数 | **0.953 – 3.787 m** | 0.55 – 4.00 | `limitStride=2.3` 完全没被执行 |
| 步频 = 步数/时长×60 | **47.2 – 128.5 步/分** | 40 – 200 | `limitStepFrequency=300` 也没执行 |
| 零速点占比 | 1.28% – 4.94% | 0.2% – 15% | |
| 暂停点占比（`i=true`） | 0.15% – 6.08% | 0.05% – 15% | |
| 采样间隔 | 中位 1000 ms，最大 **30 s**（30 个空档） | 中位 1000±15 ms | 每条记录还有 6–29 个 `dt=0` 的重复秒 |
| `t` 的毫秒抖动 | 只取 {0, 1, 998, 999}，**1125/4984 点不在整秒** | 允许 ±2 ms | 曾有实现要求整秒 → 会拒掉全部真实记录 |
| 链长 / 上报里程 | **+0.53% … +37.1%** | 下限 −0.2% 为硬，上限 +45% 只提醒 | 服务器不按点位重算 |
| `stepNumbers` 段数 | 15 – 23 段 | 8 – 30 | |
| 单段步数 | **0 – 171**（95、73、56 都出现过） | 20 – 180 | 不是恒定的 110–210 |
| 点数 | 790 – 1346 | 300 – 1500 | |
| 开始时刻 | 18:14 – **21:10** | 05:00 – 22:00 | 无硬性时段限制 |
| `s` 中位数 | 1.53 – 3.58 m/s | 0.3 – 6.0 为硬 | |
| `s` 峰值 | 最大 10.26 m/s | >10.5 提醒，>12 硬 | |

## 5. 合格配方（施工单）

以 2 km 场次为例，目标值直接照抄区间中位：

| 项 | 取值 | 依据 |
| --- | --- | --- |
| `sportType` | `1` | 只有阳光跑计成绩 |
| 距离 | **2.12 – 2.30 km**（≥ rangeSetting×1.06） | 合格记录 2.010–2.140；留余量避开 2.000 贴线 |
| 时长 | **900 – 1 000 s**（配速 7′00″–8′00″/km） | 落在 6–21 min 窗口中部，离 10′00″ 边界远 |
| 步数 | `max(stepSetting×1.05, ⌈距离/1.05⌉)` → 约 **2 100 – 2 400** | 1015 也能过，但 2 100 附近更像真人（步幅 1.0 m） |
| `stepNumbers` | 60 s 分桶，`sum == step`，末段允许 0 | `[回显]` |
| 点位 | 1 点/秒、9 键字符串、6 位小数、`t` 毫秒 | `[回显]` |
| `identify` | `uuid4()` | 被罚记录是 `"1"` |
| 设备 | `3.6.814 / iPhone / iPhone 17 Pro / iOS / 27.0.1` | `[回显]` |
| `environment` | 11 项探测全 `false` + `checksum` 自洽 | `[逆向]` |
| 人脸 | 起点/中间（按 `middleFaces` 比例）/终点三类 | 人脸是最短路口 |
| 提交后 | 回读 `getExerciseRecord` → 看 `sportStatus == "1"` 且 `reachRange == sportRange` | `[回显]` |

**顺序**：先 `getExerciseSetting` 拿 `rangeSetting / stepSetting / startQualifiedTime /
endQualifiedTime / geofence / middleFaces`，再生成轨迹，再传人脸，最后提交。

## 6. 反例清单（每一条都真实踩过）

| 现象 | 根因 | 修法 |
| --- | --- | --- |
| `运动步数不符合131310` | `step=999 < stepSetting=1000` | 步数 ≥ `stepSetting`（我们按 ×1.05 起） |
| `数据异常-作弊嫌疑` | `identify="1"`、`sportRange=2.000` 贴线、`sportTime=1200` 整、配速 `10'00"` 贴边、`appVersion 2.0.23` + Xiaomi | 五项一起换：UUID、留 6% 余量、非整数时长、配速居中、新设备画像 |
| `人脸对比超出规定范围` | 中间人脸的识别位置不在允许距离内 | 按 `middleFaces` 比例取点，且比例点本身在允许区间 |
| 提交成功但 `reachRange=0.000` | 该条未计入（判不合格 / 自由跑 / 配额已满） | 用 `reachRange` 判断，不要看 `status` |
| 点位被服务端清空 | 被判定为作弊的记录，`gitudeLatitude` 返回 `null` | 事后无法复盘点位，提交前必须本地留档 |
| `remark` 写着合格但仍被拉黑 | `-黑名单15` 是账号级处罚，与单条判定无关 | 看 `va`（`正常` / `我要申诉`）与账号状态 |

## 7. 账号级因素（与单条记录无关）

- **黑名单 15**：提交那一刻挂到账号上，事后"整改"才解除；解禁前 `getExerciseSetting` 返回 999/`code:1`，
  但 `addExerciseRecord` **不检查封禁** —— 所以封禁期仍能提交，只是继续累计处罚 `[逆向]`。
- **每日 1 条**：`sum.sunRun` 的 `succeed` 计数与 `leaveTotalCountZong` 一起限流。
- **学期配额**：`qualifyTotalCount = 40` 条 / `qualifyTotalRange = 80.0` km，已用 6 条 / 14.2 km。
- **时间段**：没有硬性时段限制，但 05:00–22:00 之外提交的样本我们没有（保守起见避开凌晨）。

## 8. 字段语义陷阱（本项目踩过的坑，全部影响合格判断）

| 字段 | 坑 | 正确语义 |
| --- | --- | --- |
| `totalRange` | 私有接口是"单次要求"，公有接口变成**阶段累计** | `14.200` = 学期已跑里程；单次门槛是 `rangeSetting` |
| `startQualifiedTime` / `endQualifiedTime` | 被当成"早上 6 点 / 晚上 21 点" | 是**分钟**：时长窗口 6–21 min，超距离时按比例放大（4.01 km → 41 min） |
| `stride` / `avgStep` | 被当成判定依据 | 服务器算的展示值：`stride = sportRange×1000/step×100`（cm） |
| `isValid` | 以为回显 `null` 就是不合格 | 服务器重算，回显不可信；看 `sportStatus` / `reachRange` |
| `okPointList` | 以为必须 `"[]"` | App 自己两种都有：列表视图 `"[]"`、详情视图 `null` |
| `uploadType` | 以为要转成整数 | 8 条记录全是字符串 `"0"` |
| `reachRange` | 被忽略 | 最省事的判据：等于 `sportRange` 才算计入 |
| `remark` | 看到 `合格` 就放心 | 后面可能跟着 `-黑名单15` |
| 点位 `c` | 被当成"第几秒" | GPS 序号，起点 0–15，可跳号，与秒无关 |
| 点位 `t` | 被要求整秒 | 毫秒时间戳，±2 ms 抖动、同秒重复都正常 |

## 9. 怎么自检

```bash
# 14 条真实记录回放：5 条合格必须 0 误杀，3 条被拒必须命中对应闸门
python tools/audit_gates.py

# 全量回归（含点位形态、迁移、旧版等价性）
python -m pytest tests -q
```

`compliance.py` 的三档模式：

| 模式 | 致命层 | 用途 |
| --- | --- | --- |
| `strict` | 协议 + 硬闸门 + 经验区间 + 自设 | 本地最保守自检 |
| `balanced`（默认） | 协议 + 硬闸门 | 真实提交前 |
| `compatible` | 只有协议 | 想验证"服务器到底卡不卡"时 |
