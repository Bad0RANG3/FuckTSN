# 体适能 App 逆向笔记：成绩「合格」到底由什么决定

> 本文记录对一个校园跑 App（包名 `com.bxkj.student`，本仓库复现其通信协议）做的静态逆向、
> 运行期对抗与服务端实测，结论落到 `compliance.py` 的分档门禁与 `docs/合格规格.md`。
> 所有标识符、学校、账号、坐标都已脱敏；文中「某次记录」指一次被服务端判为合格的提交。
> 文中不含任何真实学号、姓名、校内 ID 或密钥。

---

## 0. 一句话结论

服务端判定一次跑步是否合格，不看你的手机做了什么，而看**你提交的那份 JSON 在物理上、统计上是否自相矛盾**。
所以真正的合格条件是：**点位结构对、字段类型对、距离与点串一致、配速/步幅/步频落在人类区间、设备画像与历史一致、不重复提交**。
`compliance.py` 就是把这 19 条写成代码，任一条不过直接中止上传。

## 1. 逆向对象与工具链

| 项 | 值 |
| --- | --- |
| 包名 | `com.bxkj.student`（体适能） |
| 体积 | 136 MB（含百度人脸模型、EasyAR、高德地图、Bugly） |
| dex | `classes.dex` 76,615,096 B，magic `dex\n035` |
| 加固 | 网易易盾（见第 2 节） |
| 反编译 | jadx 1.5.7（`jadx-1.5.7-all.jar`，Java 17）、`dexscan.py`（自写 dex 字符串提取器） |
| 动态 | MuMu 模拟器（Android 15，`adb root` → `u:r:su:s0`）、frida-server 17.27.2 |
| 网络 | 抓包 / 复算：本仓库协议层（RSA + AES + md5 签名链） |

`dexscan.py` 的做法：直接扫 dex 文件里的 UTF-8 串（含 CJK），按关键词分组落盘。
**关键点：dex 的字符串区即使被加固，也没有加密**——类名、字段名、SQL DDL、中文提示语全在里头。
这就是能在「代码读不了」的情况下仍然还原出判定逻辑的原因。

## 2. 加固与分析受阻的真实情况

APK 里三块 native 库：

| 库 | 大小 | 作用 |
| --- | --- | --- |
| `libxeno_native.so` | 21.6 MB | 易盾主壳（dex 解密、反调试、完整性校验） |
| `libSecShell.so` | 1.2 MB | 安全检测（root / USB / Magisk / 模拟器 / hook） |
| `libtsnsecret.so` | 12.0 MB | 业务 JNI（签名、AES、RSA、md5、路由常量） |

`classes.dex` 的 header 自报 `string_ids=9367 / type_ids=1116 / class_defs=541`，`data` 段只到
3,117,664 字节，但文件是 76 MB——后面 73 MB 全是易盾的加密指令区与 `0f0f0f` 填充。
jadx 只能反出 541 个壳类，跑几分钟后卡死。

运行期对抗实测（三个方向全部被封死）：

1. **frida**：`frida-server` 一驻留，App 启动数秒内自杀；`frida-dexdump` 报
   `script has been destroyed`。易盾扫 `/proc/self/maps`、线程名与端口。
2. **`/proc/<pid>/mem` 直读**：即使 `adb root`，`dd` 读内存页返回
   `read error: I/O error`（内核级 `ptrace_may_access` 拒绝），App 随后 `has died: fg TOP`，无 FATAL 栈。
3. **落地文件**：`/data/data/com.bxkj.student/.cache/classes.dex` 只有 4 字节占位，
   `.cache/classes.dve` 24 B，`cache/oat_primary/x86_64/base.art` 8,320 B，`.payload/` 为空——
   解密后的 dex 只在内存里存在过。

**因此改走三源合证**，而不是继续和壳硬碰：
静态字符串（DDL、提示语、字段名）+ native 导出符号 + 服务端真实记录（合格样本与被处罚样本）。

附带发现：本地库 `databases/TSNStudent.db` 是 **SQLCipher** 加密（dex 内有
`Lnet/sqlcipher/database/SQLiteDatabaseHook;`），文件头 `a5 fe a3 a1`，不是 SQLite magic。
想读它得从 `libtsnsecret.so` 里扒密钥推导——性价比极低，因为服务端记录已经能说明一切。

## 3. 从字符串区挖到的东西

### 3.1 本地 `sports` 表（App 自己的待上传队列）

```sql
CREATE TABLE IF NOT EXISTS `sports` (
  `identify` TEXT NOT NULL, `userNumber` TEXT NOT NULL, `sportsType` TEXT NOT NULL,
  `sportsSet` TEXT NOT NULL, `startTime` ..., `endTime`, `countTime`, `distance`,
  `gpsDistance`, `latLngList`, `stepList`, `passLatLngList`, `isFaceOut`,
  `faceDetectCount`, `uploadType`, `isException`, `startFace`, `midFace`, `endFace`,
  `isValid` TEXT NOT NULL DEFAULT '0', `faceCheckingDistance`, `pauseLatLng`,
  `isOpenDevelop` TEXT NOT NULL DEFAULT '0', `confirmCount` INTEGER NOT NULL,
  `momentIsValid` INTEGER NOT NULL, `faceOutIndex` TEXT NOT NULL DEFAULT '',
  `remarkId` TEXT NOT NULL DEFAULT '', PRIMARY KEY(`identify`))
```

这张表说明：`identify`（一次跑步的 UUID）、`latLngList`（点串）、`stepList`（分段步数）、
`passLatLngList`（打卡点）、`isValid`/`remarkId`（服务端判定回写）、`isOpenDevelop`（开发者模式标记）
就是提交体的骨架。`pauseLatLng` 说明暂停点也要上报——对应点串里的 `i` 字段。

### 3.2 环境检测表（`safe` / `oppo` 到底存什么）

```sql
CREATE TABLE IF NOT EXISTS environment (deviceId TEXT NOT NULL,
  safe TEXT DEFAULT '', oppo TEXT DEFAULT '', PRIMARY KEY(deviceId), UNIQUE(deviceId))
```

配合 `libSecShell.so` 的导出符号，语义完全对上了：

```
check_root   check_usb   checkUsb   is_magisk_check_process   __b_a_n_g_c_l_e__check1234567_
```

`safe`/`oppo` 两个 JSON 就是这些检测的结果集。本仓库 `tsn_environment.py` 里
`clean_device_signals()` 把全部信号置 false 的用意即在此——**不是为了骗过手机，而是为了让提交体
里没有「root=true / hook=true」这种自证其罪的字段**。

### 3.3 客户端提示语（判定条件的最直白来源）

逆向时最省事的做法是读 App 自己写的报错文案，它们几乎等于判定规则说明书：

- `系统检查到疑似模拟定位，已被系统记录` / `系统检测到当前手机为模拟位置` / `卸载虚拟定位软件`
  → 位置来源（`Location.isFromMockProvider`）会被上报。
- `您的设备没有GPS模块或者GPS模块异常`、`当前GPS信号弱`、`GPS星数：`
  → 卫星数、定位精度参与判定；点串里的 `c`（GPS 序号）必须单调递增，就是在证明「GPS 一直在正常出点」。
- `加速度传感器无法使用`、`运动步数不符合`、`运动step不符合`
  → 步数与传感器一致性是硬条件；`stepNumbers` 不是装饰。
- `不允许重复上传，如有疑问请联系管理员`
  → 同一次 `identify` 不能二次提交。
- `数据异常，可以替祖国拿金牌了`
  → 速度/距离超出人类极限时的专用吐槽。
- `是否合格：合格/不合格/待批改`、`达标步数:`、`达标里程：3.0KM`
  → 判定分三态，`待批改` 说明有人工复核通道。

## 4. 提交体的真实结构（最容易踩的坑）

历史合格记录里的 `gitudeLatitude`（拼写是服务端自己的锅）是一个数组，每个元素**恰好 9 个键，
且全部是字符串**：

```json
{"a":"-23.533768","c":"15","e":"0","i":"false","l":"1","m":"0","o":"13.621175","s":"0.467176","t":"1793020234000"}
```

| 键 | 含义 | 实测语义（关键） |
| --- | --- | --- |
| `a` | latitude | 6 位小数字符串 |
| `o` | longitude | 6 位小数字符串 |
| `t` | 毫秒时间戳 | **对齐整秒**，采样间隔基本固定 1000 ms |
| `s` | 瞬时速度 m/s | 含 0 值静止段；峰值 5–10 m/s |
| `c` | **GPS 原始点位序号** | 起点 0–15 不等，基本 +1，可跳号；不是秒偏移 |
| `e` | **累计步数** | 单调不减，末值 == 记录 `step` |
| `i` | 暂停标志 | 字符串 `"true"`/`"false"`，结束前会置 true |
| `l` | 常量 | 恒 `"1"` |
| `m` | 常量 | 恒 `"0"` |

踩过的坑（都真实发生过）：

- **类型**：写成数字（`"s":0.467176` 无引号）历史无先例，服务端按字符串解析会出错。
- **`c` 语义**：把它当「秒偏移」写 1,2,3…627，等于宣称 GPS 一个点没丢、序号还从 1 开始——假的。
- **缺 `m`**：9 键变 8 键，字段集不一致。
- **`t` 不对齐整秒**：App 的采样是整秒触发的，毫秒零头等于暴露「这不是真机采的」。
- **噪声虚增距离**：给点串加噪声后，服务端用点串重算的距离会比上报的 `sportRange` 大几个百分点。
  `1%` 是安全线，本仓库实测 +0.11%。

## 5. 服务端判定：19 条硬条件

下表就是 `compliance.py` 的实现依据。「出处」列说明阈值不是拍脑袋：

| # | 条件 | 阈值 | 出处 |
| --- | --- | --- | --- |
| 1 | 点位键集 == 9 键 | 精确相等 | App 原生点串 |
| 2 | 所有值均为字符串 | — | 同上 |
| 3 | `a`/`o`/`s` 6 位小数 | 精确 | 同上 |
| 4 | `t % 1000 == 0` | ≥98% | 采样节拍 |
| 5 | `c` 起点 0–15、不回退 | — | 5 条合格记录 |
| 6 | `e` 单调、末值 == `step` | — | 合格记录 |
| 7 | `i` ∈ {true,false}、末点 true | 占比 0.2%–9% | 合格记录 |
| 8 | `l`=1、`m`=0 | 全部 | 合格记录 |
| 9 | 点数 300–1500 | 2 km 实测 718–1041 | 合格记录 |
| 10 | 采样间隔中位数 1000 ms | 非 1/2/3 s 占比 ≤3% | 合格记录 |
| 11 | 静止点占比 | 0.2%–10% | 合格记录 |
| 12 | 速度中位数 | 1.2–3.6 m/s | 合格记录 1.53–3.58 |
| 13 | 速度峰值 ≤ 10.5 m/s、峰均比 ≤ 6.0 | — | 合格记录 5.15–10.26 / 2.17–5.92 |
| 14 | 点串累加距离比上报距离 **长 +0.2%~+6%** | 负偏差即错 | 真机实测 +0.5%~+37%（服务端不拿点串重算）|
| 15 | 轨迹包络 ≥ 120 m | — | 合格记录 188–539 |
| 16 | 围栏越界 ≤ 10% | — | 合格记录自身 0–4.3% |
| 17 | 里程 ≥ 达标线（通常 2000 m）、≤ 3000 m | 校规 | `getExerciseExplanation` |
| 18 | 配速 180–600 s/km（内部收紧 330–510） | 校规 3′–10′ | 同上 |
| 19 | 步幅 0.62–1.20 m、步频 145–195 spm | — | 人类生理区间（早期按假样本标定过 1.85–2.20 m，已推翻）|

额外三条记录级检查：

- `stepNumbers` 段数 8–30、每段 110–210（末段 1–210）、总和 == `step`（App 是 60 s 一桶）。
- `identify` 必须是标准 UUID。
- 配速串必须用 `′`(U+2032)、`″`(U+2033)，形如 `7′02″`。
- 设备画像（`appVersion`/`brand`/`model`/`system`/系统版本）与历史合格记录一致。
- 同一自然日不重复提交。

## 6. 一次被处罚的样本说明了什么（脱敏复盘）

处罚形态：`remark = 数据异常-作弊嫌疑有疑问请联系客服-黑名单15`，`status = 0`，账号级禁跑 15 天。

该次提交的特征（全部来自服务端回读，不是推测）：

| 特征 | 处罚样本 | 合格样本 |
| --- | --- | --- |
| 配速 | 恰好 `10′00″`（撞规则上限） | 6′00″–8′12″ |
| 时长/距离 | 1200 s / 2.000 km，两个整数值 | 880–1351 s / 2.05–2.09 km |
| 步幅 | 0.83 m | 0.95–3.78 m（**样本步态不可能由步行产生，不可作参照**）|
| `identify` | `"1"` | 标准 UUID |
| 设备 | Xiaomi / Android 14 / app 2.0.23 | iPhone / iOS / app 3.6.814 |
| `gitudeLatitude` | 服务端反序列化报错（不是数组） | 正常数组 |
| 点字段类型 | 数值、8 键、无 `m` | 9 键全字符串 |

教训按重要性排序：

1. **别贴规则边界**。10′00″ 是上限，写满等于自报「我是照着规则生成的」。
2. **步幅/步频是最难伪造的统计特征**。服务端只要拿 `distance / step` 一除就暴露。
   注意：不能拿「历史合格记录」反推这两项 —— 那批样本的步态参数本身超出人类区间
   （步幅 2 m、步频 69 spm），照它标定只会造出「每 0.87 秒跨 2 米」这种不可能的数据。
   本项目一律按人类生理区间重建，见第六节。
3. **设备画像突变 = 立刻可疑**。同一账号，历史全是 iPhone，突然一台 Android 14 + 老版本 App。
4. **JSON 结构畸形比数据错更致命**。服务端解析失败时会直接判异常，连申诉都要人工。
5. **`identify` 不是 UUID** 等于告诉服务端「我不是 App 生成的」。

反向推论：既然处罚是「15 天 + 账号级」，那么**协议层无法绕过**——不要再试图换设备指纹硬撞，
先把提交体做对。

## 7. 门禁的实现形态

```
生成轨迹 → to_legacy_points(9 字段字符串) → 拼 submit_extras
        → compliance.check_submission(...)  ← 19 + 5 条
        → 通过才 addExerciseRecord → 回读 sportStatus == '1'
        → 成功后 record_success() 落 run_history.json（供「同日一次」判定）
```

`check_submission(points, step_numbers, meta, fence=None, history=None)` 返回
`ComplianceReport`，`error` 级问题会 `raise ComplianceError` **阻止上传**。
设计取向很明确：**宁可今天不跑，也不要再产生一条 `status=0` 的记录**。

调试命令：

```bash
python run.py selftest --count 5     # 合成跑道离线跑门禁，不需要账号/网络
```

`selftest` 用一条 300 m 的合成环形跑道（默认 30.0N/120.0E），与任何真实校园数据无关，
任何人 clone 下来都能直接验证门禁逻辑。

- 服务端判定规则会变。门禁是「减少被抓概率」的工具，不是「保证合格」的承诺。

## 9. 后来的两次推翻（v4）

逆向最容易犯的错不是看错代码，而是**把伪造样本当成 ground truth**。项目里踩了两次，都记在这里。

### 9.1 「服务端会重算距离」是错的

最初按常识假设服务端会拿 `gitudeLatitude` 重算里程再和 `sportRange` 比。后来用真实合格记录反推：

| 样本点数 | 上报里程 | 点串逐点累加 | 偏差 |
|---|---|---|---|
| 790 | 2090 m | 2865 m | **+37.1%** |
| 890 | 2050 m | 2309 m | +12.6% |
| 1024 | 2010 m | 2115 m | +5.2% |
| 1346 | 4010 m | 4030 m | +0.5% |
| 934 | 2020 m | 2038 m | +0.9% |

37% 的偏差照样判「合格」并按 2.09 km 计入统计 → **服务端信客户端的 `sportRange`/`gpsDistance`，
不拿点串重算**。原因也合理：手机上报的是平滑轨迹，上传的是带噪原始点，累加天然偏长。

所以生成器改成「上报 = 平滑规划长度，点串累加比上报长 +0.3%~+2.3%」。反过来说，
如果点串累加**短于**上报，才是真的可疑（说明点被凭空删了）。

### 9.2 历史「合格记录」不是跑步数据

早期 19 条阈值里有 4 条是按「历史合格记录」标的，其中步幅/步频完全跑偏（2.05–3.78 m / 46–126 spm）。
复核后确认：那批样本的步态参数本身不可能由步行产生（步幅 2 m 而步频不足 70 spm，
等价于每秒跨两米），另有几条是整千步的随手填写。也就是说：

- 「步幅 2 m 也合格」不等于「服务端不查步幅」，只等于「那次的样本没有被规则命中」；
- 拿它当基线，生成器会造出「每 0.87 秒跨 2 米、步频 69」的数据 —— 一眼假。

v4 全部改回人类区间：步幅 0.62–1.30 m（常用 0.78–0.95）、步频 150–190 spm、2.1 km 约 2200–2800 步。
同时把「60 s 步数桶」从「30–90」改成「110–210」，因为真人慢跑一分钟就是 150–180 步。

教训写进流程：**标定参数前先确认样本是不是真的**。伪造数据只能证明「服务端没抓到那一次」，
不能证明「规则不存在」。
